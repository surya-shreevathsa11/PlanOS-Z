--------------------------------------------------------------------------------
1. WHY THIS EXISTS (PROBLEM STATEMENT)
--------------------------------------------------------------------------------
Embedded devices today usually get logic in one of three weak ways:

  A) Hardcoded firmware loops (inflexible; every feature = reflash).
  B) Ad-hoc shell/MQTT commands (no timing guarantees; unsafe composition).
  C) "AI controls GPIO" demos (impressive demo, zero systems credibility).

Industry systems (vehicles, industrial controllers, robots) need something
closer to:

  - declared capabilities
  - validated jobs/plans
  - resource conflict detection
  - deadlines / worst-case awareness
  - observability and replay when something fails
  - a path from simulation -> hardware without rewriting the core

PlanOS-Z exists to bring that *execution-plane* discipline to Zephyr as a
coherent open project — not as another sample app.

This is intentionally aligned with your background (vehicle ECU, modular C++,
NDJSON telemetry, ESP32, host serial agents). PlanOS-Z should feel like the
*next abstraction layer* above "I wrote firmware that toggles pins."

4. CORE CONCEPTS (MENTAL MODEL)
--------------------------------------------------------------------------------
  SKILL
    A named, versioned capability implemented in C on Zephyr.
    Example IDs: sensor.read, led.blink, wait, power.sleep, gpio.write

  CONTRACT
    Metadata every skill must publish before it can be registered:
      - skill_id + version
      - argument schema (types, ranges, enums)
      - output schema
      - declared resources (e.g. i2c0, gpio2, led0, radio)
      - WCET estimate (worst-case execution time budget) or duration model
      - power class (ACTIVE_HIGH / ACTIVE_LOW / SLEEP)
      - permissions / safety class (SAFE / HAZARDOUS / REQUIRES_CONFIRM)

  PLAN
    A job submitted to the device: a DAG of steps (not only a linear list),
    optional conditions, global deadline, required permissions.

  IR / BYTECODE
    Host compiles Plan -> compact IR (CBOR or custom bytecode). Device does
    not trust free-form English or unchecked JSON forever; v1 may accept
    validated JSON, but architecture targets compiled IR.

  ADMISSION
    Before any side effect: runtime checks that the plan is known, args are
    valid, resources don't conflict illegally, and deadline vs WCET is
    plausible. Returns ACCEPT or REJECT with a reason code.

  EXECUTION
    Scheduler runs ready steps, respects dependencies, locks resources,
    enforces timeouts, emits trace events, returns structured results.

  TRACE / REPLAY
    Every admit/reject/start/end/error is logged. native_sim can replay a
    trace or re-run a plan deterministically for CI and debugging.

  BACKEND
    Platform binding: native_sim fakes first; ESP32 real GPIO/sensors later.
    Core runtime must not #ifdef itself into unreadability per board.

5. FLAGSHIP EXAMPLE (USE IN README + DEMOS)
--------------------------------------------------------------------------------
Goal submitted to PlanOS-Z:

  "Read temperature and humidity in parallel.
   If temperature > 30 C, blink warning LED 5 times.
   Else enter light sleep for 10 seconds.
   Entire job must finish within 2000 ms or abort.
   Requires resources: i2c0, led0."

Expected serious behaviors:

  CASE A — admission reject (shows depth):
    REJECTED  PLAN_DEADLINE_INFEASIBLE
    detail: estimated_wcet_ms=2400 deadline_ms=2000

  CASE B — resource conflict reject:
    REJECTED  RESOURCE_CONFLICT
    detail: steps A and B both need exclusive i2c0 without share mode

  CASE C — accept + run:
    ACCEPTED
    TRACE:
      admit ok
      fork A sensor.read(temp) / B sensor.read(humidity)
      join
      cond temp=31.2 -> led.blink(times=5)
      done total=1180ms
    RESULT: ok

This example is the north star. If your demo cannot show REJECT for a good
reason, the project is still too shallow.

6. SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------

  +------------------+       +------------------------+
  | Plan authoring   |       | Skill IDL (YAML/JSON)  |
  | (YAML/JSON plan) |       | contracts per skill    |
  +--------+---------+       +-----------+------------+
           |                             |
           v                             v
  +------------------+       +------------------------+
  | planoszc         |<------| codegen                |
  | plan compiler +  |       | C stubs, schemas, docs |
  | static checker   |       +------------------------+
  +--------+---------+
           |  IR / validated plan blob
           v
  +------------------------------------------------------+
  |                 PlanOS-Z Runtime (Zephyr)            |
  |  +-------------+  +--------------+  +-------------+  |
  |  | Ingress     |  | Admission    |  | Scheduler/  |  |
  |  | (shell/UART |  | Controller   |  | Executor    |  |
  |  |  / later    |  |              |  | (DAG)       |  |
  |  |  net)       |  +--------------+  +-------------+  |
  |  +------+------+         |                 |         |
  |         |                v                 v         |
  |         |         +--------------+  +-------------+  |
  |         |         | Resource     |  | Skill       |  |
  |         |         | Manager      |  | Registry    |  |
  |         |         +--------------+  +-------------+  |
  |         |                                  |         |
  |         v                                  v         |
  |  +--------------+              +------------------+  |
  |  | Trace / Log  |              | Backend HAL      |  |
  |  | + Replay     |              | native_sim|ESP32 |  |
  |  +--------------+              +------------------+  |
  +------------------------------------------------------+

Design rules:
  - Runtime core has ZERO dependency on a specific sensor breakout.
  - Backends implement a narrow HAL (led, delay, sensor fake/real, etc.).
  - Skills call HAL + Zephyr primitives; they do not own the scheduler.
  - Prefer zbus or message queues between ingress, admission, executor.
  - Deterministic behavior on native_sim is a first-class requirement.

8. SKILL IDL (CONTRACT) — REQUIRED FIELDS
--------------------------------------------------------------------------------
Example: idl/skills/led.blink.yaml

  skill_id: led.blink
  version: 1
  summary: Blink an LED N times with on/off durations.
  args:
    times:   { type: uint16, min: 1, max: 50 }
    on_ms:   { type: uint32, min: 1, max: 5000, default: 200 }
    off_ms:  { type: uint32, min: 1, max: 5000, default: 200 }
  returns:
    blinked: { type: uint16 }
  resources:
    - { name: led0, mode: exclusive }
  wcet_ms: "times * (on_ms + off_ms) + 20"
  power_class: ACTIVE_LOW
  safety_class: SAFE
  permissions: [ACTUATE_LED]

Codegen must emit:
  - arg validators
  - registry table entries
  - documentation fragments
  - host-side schema used by planoszc

Adding a skill in a "great" project means:
  1) write IDL
  2) run codegen
  3) implement skill handler
  4) add unit/plan tests
  5) docs update automatically or via checklist
NOT: paste a random function into main.c

9. PLAN LANGUAGE (v1)
--------------------------------------------------------------------------------
Support YAML/JSON plans with:

  - metadata: plan_id, deadline_ms, permissions[]
  - steps[] each with: id, action, args, needs[] (dependencies)
  - optional: parallel groups via independent deps (DAG)
  - optional: conditional edges (v1.1 if needed; can be host-lowered)

Example:

  plan_id: demo.parallel_sense
  deadline_ms: 2000
  permissions: [READ_SENSOR, ACTUATE_LED]
  steps:
    - id: t
      action: sensor.read
      args: { sensor: temp }
    - id: h
      action: sensor.read
      args: { sensor: humidity }
    - id: warn
      action: led.blink
      args: { times: 5 }
      needs: [t, h]
      # condition handling strategy documented in plan_language.md

v1 execution may linearize safely if DAG scheduler is phased — BUT the IR
and admission must still reason about declared deps and resources.
Do not fake "architecture" that the code cannot support; phase features
honestly (see section 12).

10. ERROR / RESULT MODEL (PUBLIC API SURFACE)
--------------------------------------------------------------------------------
Stable reason codes (extend carefully; document all):

  OK
  REJECT_UNKNOWN_SKILL
  REJECT_BAD_ARGS
  REJECT_PERMISSION
  REJECT_RESOURCE_CONFLICT
  REJECT_DEADLINE_INFEASIBLE
  REJECT_UNSUPPORTED_IR
  REJECT_SAFETY_CLASS
  EXEC_TIMEOUT
  EXEC_SKILL_FAIL
  EXEC_CANCELLED
  EXEC_BACKEND_UNAVAILABLE

Every reject/fail must be machine-readable AND human-readable.
Prefer NDJSON telemetry lines (fits your existing style) e.g.:

  {"type":"admit","plan":"demo.parallel_sense","status":"REJECT",
   "code":"REJECT_DEADLINE_INFEASIBLE","wcet_ms":2400,"deadline_ms":2000}

11. RUNTIME INTERNALS (WHAT "GREAT" LOOKS LIKE IN CODE)
--------------------------------------------------------------------------------
Admission controller:
  - schema validate
  - permission check
  - build resource timeline / conflict graph from step deps
  - estimate WCET from contracts (conservative)
  - compare to deadline_ms
  - emit admit trace

Resource manager:
  - named resources with exclusive/shared modes
  - lock acquire with timeout
  - deadlock avoidance via lock ordering OR reject-on-cycle at admission

Scheduler / executor:
  - ready queue from satisfied dependencies
  - per-step timeout from contract
  - cancellation path
  - no blocking forever without watchdog/timeout policy

Trace:
  - ring buffer on device
  - export over UART
  - golden file compare in CI
  - replay harness on native_sim

Registry:
  - static registration table (v1)
  - version field on skills
  - query command: list skills + contracts summary
